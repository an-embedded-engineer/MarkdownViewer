# コーディングルール

## 基本方針

- 本プロジェクトは Avalonia/C# 版と Tauri/React/Rust 版を同じMVP要件で比較する。
- 片方の実装で得た設計判断は、もう片方へ機械的に移植せず、技術スタックの自然な責務境界に合わせて反映する。
- 類似ロジックを見つけた場合は、重複実装より抽象化・共通化を優先して検討する。
- 関数やロジックの配置は、呼び出し箇所との近さではなく責務の所属と再利用性で判断する。
- 完了条件は変更対象に応じて `docs/rules/development_workflow.md` の検証コマンドを実行すること。

## 共通必須ルール

1. 型付きデータモデル
   - C# は `record` / `class` / enum、TypeScript は `type` / union、Rust は `struct` / enum で契約を明示する。
   - 汎用辞書や `object` / `any` による受け渡しは I/O 境界以外で使わない。
2. 例外・エラー処理
   - 例外や `Result` の失敗を握りつぶさない。
   - ユーザーに見せるエラーは英語で、原因追跡に必要な情報を含める。
3. 後方互換
   - 明示的に指示されない限り、旧経路/旧 API/旧データ解釈を残す後方互換レイヤーは実装しない。
   - 置き換え後は呼び出し側・検証・文書を更新し、最適な経路 1 つに収束させる。
4. フォールバック
   - 不必要なフォールバックを実装しない。
   - フォールバックが必要な場合は条件と理由をコメントまたは文書で明示する。
5. 関数の配置
   - メソッド/関数追加時は、その責務が特定クラス/モジュール固有か、より抽象的か、汎用的かを先に判断する。
   - 変更範囲を局所化したいだけの理由で、呼び出し箇所に近い場所へ安易に追加しない。
6. 生成物
   - `bin/`、`obj/`、`target/`、`node_modules/`、`dist/`、`publish/` をコミットしない。

## C# / Avalonia ルール

- public なクラス/メソッド/プロパティに XML Doc コメントを付ける。
- `<Nullable>enable</Nullable>` を維持し、`T?` を使う場合は呼び出し側で null チェックする。
- `reflection` / `dynamic` / `ExpandoObject` を避ける。
- ViewModel はUI状態と操作の調停を担当し、ファイル走査やMarkdown変換は Service に置く。
- `async void` はイベントハンドラを除いて使わない。

## TypeScript / React ルール

- `any` を使わず、Tauri command の戻り値も型引数付きで受け取る。
- React state は画面状態の正本を明確にし、DOM変換が必要な処理は再実行条件を明示する。
- Markdown HTML生成、Mermaid描画、リンク処理は責務を分ける。
- 相対パスやURLの扱いは専用関数へ閉じ込め、コンポーネント内に散らさない。

## Rust / Tauri ルール

- ファイルシステム操作は Rust command 側に寄せる。
- `PathBuf` と `canonicalize` によるパス検証を優先する。
- `Result<T, String>` でフロントエンドへ明示的な失敗を返す。
- `serde` の `rename_all` などで TypeScript 側とプロパティ名を揃える。

## 設計原則

- DRY: 同じ責務の重複ロジックを排除する。
- SRP: 1 クラス/コンポーネント/関数 1 責務を維持する。
- DIP: C# では Service 抽象、Tauri では command 境界を使って依存方向を整理する。
- UI とファイルシステム境界を混在させない。

## 完了前チェック

1. 変更対象のビルド・型チェックを実行する。
2. UI変更では手動確認項目を `docs/rules/development_workflow.md` に従って確認する。
3. 設計・ルール・publish手順が変わる場合は `docs/` を更新する。
